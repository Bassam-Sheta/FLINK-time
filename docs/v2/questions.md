## 2026-11-19 · T2.2 · Noted, no answer needed: clients, projects, tasks and project access

No notes, versions, rates, costs, budgets, estimates, dates or `restricted` flag. A User's tasks are those of projects they may track, so a restricted project's tasks are hidden with it.
- **Write rules.** Every write asserts, inside its transaction, that the workspace is ACTIVE, the row is in this workspace (`NOT_FOUND`: another workspace's id looks the same as a missing one), then the version (`CONFLICT`), then changes the row and writes an audit row (`CLIENT_CREATED`, `PROJECT_UPDATED`, `TASK_ARCHIVED`, `PROJECT_ACCESS_SET` and so on, with before and after). Every write bumps `gen:ws:{id}`. A duplicate name is the table's UNIQUE, so `CONFLICT` (per workspace for clients and projects, per project for tasks). Archiving what is archived is `CONFLICT`. - **Archiving a project changes nothing already recorded:** entries and a running timer keep their project and the rate snapshot taken at the stop; the project simply leaves the lists and can no longer be started on (T2.4).
- **Four mutants survive on purpose:** removing the scope assert and the `AND workspace_id = ?` from the UPDATE in `update_` and `archive_`. The row was already read with the same scope (and a row never changes workspace), so the outcome cannot differ; they stay as a second guard in the transaction.
- **A project's end date** must not be before its start date, checked against the stored start date on update (`VALIDATION` on `endDate`). Colours are free text up to 20 characters, as the spec gives no format.

## 2026-11-18 · T2.1 · Noted, no answer needed: workspaces and members

Pinned by `tests/v2/act-workspaces.test.js` (48 tests) and `tests/v2/timer-stop.test.js`. The patterns here are the ones every later write handler follows.

- **The write-handler pattern.** A handler may read before its transaction (to build audit rows), but must not throw on what it finds, because on a retry of a request that already committed it finds the state that request left. So it refuses *through* the transaction (`Main.refuse_`): the request-log check runs first and returns the stored result for a retry, otherwise the failing assert throws the error. A write that turns out to change nothing still records the request (`Main.noop_`). Every write ends with `Main.commit_`, which stores the result and tells the handler whether this was a retry, so cache bumps and mails are not repeated. `Auth.assertWorkspaceActive_(tx, id)` is the section 7.1 rule 5 assert every workspace write includes. The checks that matter (version, existence, active workspace, no timer left) are asserts inside the transaction; the early reads only give quick answers, and a race test for each shows the transaction winning.
- **One consequence:** a retry of `workspaces.archive` after it worked gets `FORBIDDEN` ("archived"), not the stored result, because the pipeline refuses a write in an archived workspace before the handler runs. The archive itself is not repeated and nothing is stopped twice; the user sees an error for something that worked and a reload shows it archived. Making `archive` `readOnlyOk` would fix it but would let one write action past the pipeline's archived check, which the matrix test forbids on purpose.
- **`workspaces.list`:** a user's list comes from the cached account (no database call): id, name, status, time zone, week start, own role. A Super Admin gets every workspace from the database, with code and version, and their own role or `null`.
- **A time zone change** inserts or refreshes the row `export_state` name `tzrewrite:{workspaceId}`, status `PENDING`, `cursor_json` `{"at","from","to"}`, in the same transaction. This is the queue T2.9's resumable job reads; `export_state` was the only existing table that holds job state by name. A second change before the job ran replaces the target and keeps `from` as what the database held at that moment.
- **`workspaces.archive`** stops every running timer in the workspace in the same transaction as the archiving (`stop_reason = 'USER'`, capped at `AUTO_STOP_HOURS`), with one `TIMER_STOPPED` audit row per timer under actor `SYSTEM`. It reads the timers first; if a timer starts or changes between that read and the transaction, an assert makes the whole thing `CONFLICT` ("try again") rather than leaving a running timer in an archived workspace. The audit `after` values come from the earlier read, so they are right unless the timer was edited in that same instant, in which case the entry in the database is right and the audit row is a few seconds stale.
- **`members.remove`** stops only that user's timer if it runs in *this* workspace (a user has at most one timer, anywhere). `members.add` of someone removed earlier brings them back as a plain `MEMBER`: only a Super Admin makes a workspace admin. Nothing stops a workspace admin removing another workspace admin or themselves; the spec names no such rule and I did not add one.
- **`members.setAdmin`** follows section 6.2 and D6 to the letter: the target must be an active member whose account role is Admin or Super Admin; granting asserts the number of their *active* workspaces where they are already workspace admin is below `COALESCE(admin_ws_limit, ADMIN_MAX_ACTIVE_WORKSPACES)` (`POLICY`, `details.rule = ADMIN_MAX_ACTIVE_WORKSPACES`); archived workspaces do not count; asking for what already is the case changes nothing, whatever the limit. As written the limit also applies to a Super Admin target, who passes every workspace check anyway; say if Super Admins should be exempt.
- **Cache:** every change bumps `gen:acct` and `gen:ws:{id}`, so a member, a removed member and a Super Admin see the change on their very next request (tests do this).
- **`ActTimer.addStop_`** (the three statements of section 6.4 plus an existence assert) was needed here for archiving and removing, so it exists now in `ActTimer.gs` with its own tests; T2.4's `timer.stop`, T2.7 and T3.4 use it.
- The rule-4 todo for the D6 limit in `server-rules.test.js` is now a real test.

## 2026-11-18 · T1.11 · Noted, no answer needed: the setup page and the owner functions

Pinned by `tests/v2/setup.test.js`. The owner-check question further down is implemented as proposed there.

- **The owner check** is `Setup.requireOwner_()`: the active user (who is actually running) must equal the effective user, and both must equal `OWNER_EMAIL` once it is recorded; before setup the deployer is the owner. A blank on either side is refused. Every owner function and `setupSubmit` start with it, and a test fails if any top-level function without a trailing underscore exists that is not on the list of section 2.1 (the page, `setupSubmit`, the owner functions, `job*`).
- **The setup page** is `/exec?view=setup`, served with `DEFAULT` frame mode and built inline in `Setup.gs` (`files.json` has no separate setup file). For the owner before setup it is a form (URL, two tokens, company domain, alert address); for a visitor, or after setup, a plain message with nothing to fill in. It makes no database call and shows no stored value. The two token fields are password inputs and answers are shown with `textContent`.
- **`setupSubmit` is single use and safe to repeat after a failure.** It checks the whole form first (nothing is written if any field is wrong), stores the connection settings and `OWNER_EMAIL`, creates only the keys that do not exist yet (regenerating the audit key after rows were sealed would break the chain), applies the migrations, creates the owner's root Super Admin account (D1) unless a root exists, and only then sets `SETUP_DONE = 1`. The URL is converted from `libsql://` to `https://`, lower-cased, no path; the two tokens must differ; and the company domain must be the domain of the owner's own address, or the owner would lock themselves out. Secrets are never returned, logged, mailed or audited.
- **`ownerGrantSuperAdmin(email)`** takes an address in the company domain, creates the account or promotes and re-activates the existing one in one transaction with an audit row (`SUPER_ADMIN_GRANTED`, actor `SYSTEM`), drops the account cache, and mails `ALERT_EMAIL` (plan: an alert on every Super Admin change). Someone who already is an active Super Admin is left alone (no audit row, no mail). It never makes a root.
- **`installTriggers`** builds the schedule of section 8, with two triggers for `jobBackup` (weekly, and every 10 minutes so an unfinished backup resumes; the job does nothing unless one is RUNNING). It **refuses, changing nothing, while any job function it names does not exist**, because a trigger for a missing function only fails later, by mail. So until T2.7, T2.9 and T4.4 define `jobSealAudit`, `jobAutoStop`, `jobDailyExport`, `jobVerifyChain`, `jobBackup`, `jobPurge` and `jobHealth`, running it gives `INTERNAL` naming the missing ones.
- **`ownerMaintenance(on)`** is a boolean switch for `MAINTENANCE`. Section 8 lists it but says nothing about its effect, so: while it is `1`, the request pipeline answers every request for a known action with a retryable `DB_UNAVAILABLE` ("FLINK Time is down for maintenance. Try again in a few minutes.") before anything else, without a database call; the page itself is still served. Section 4.3 has no code of its own for it, and the page already retries `DB_UNAVAILABLE` three times, so a short maintenance shows as a brief delay.
- **Key rotation** (`ownerRotateAuditKey`, `ownerRotateTotpKey`) adds key version n+1 and makes it current; the old key stays, because old rows and secrets still need it. The audit row (`AUDIT_KEY_ROTATED` or `TOTP_KEY_ROTATED`, versions only) is written first, so a failed record means no rotation, and `ALERT_EMAIL` is told. Re-encrypting existing TOTP secrets under the new key is not done here (they keep decrypting with the key version stored beside each); T3.1 decides how a secret is re-encrypted.
- **`ownerIssueRootEnrollCode`** is not here: it needs the enrollment code format and the secret cipher, which come with T3.1 and T3.2, and it will be added to the allowed public functions then.

It is the one platform behaviour the owner check depends on; the Phase 0 sessions are the place to confirm it.

## 2026-11-18 · T1.10 · Noted, no answer needed: how the audit chain fills the gaps in section 5.5

Each point is pinned by a test in `tests/v2/audit.test.js`, which also recomputes every chain independently with `node:crypto`.

- **`Audit.seal_()` is the whole sealer, lock included** (`tryLock(0)`, skip if busy, release in `finally`). The trigger entry point `jobSealAudit`, the `job_runs` row and the 4.5-minute stop that section 8 asks of every job belong to the job runner, which has no ticket of its own: it arrives with the first job, T2.7. T1.11's `installTriggers` will name `jobSealAudit`, so T2.7 must define it before launch; until then nothing calls the sealer.
- **One run seals at most 200 rows** (section 5.5 says `LIMIT 200`), so a backlog of N rows takes N/200 minutes. At the expected volume that is never visible.
- **A gap is also reported when it sits at the start** (first unsealed `seq` is not `head.seq + 1`). One security event `AUDIT_SEQ_GAP` and one mail per set of findings; its request id is derived from the findings (`sec:gap:{hash}`), so a run that fails after recording it and is repeated does not record or mail it twice. The mail says which numbers are missing, nothing else.
- **An unsealed row whose `seq` is at or below the chain head** (it cannot happen by itself) is not sealed, because sealing it would put it in the wrong place in the chain. It goes into the same `AUDIT_SEQ_GAP` event (`below`), stays unsealed, and the rows above the head are sealed as usual.
- **The checkpoint** (`CHAIN_CHECKPOINT = {"seq","hash","at"}`) is written after every successful seal, only forward, and an unreadable one is replaced. The verifier reports a checkpoint that is unreadable, ahead of the head, whose row is missing, or whose hash differs (types `CHECKPOINT_UNREADABLE`, `CHECKPOINT_AHEAD`, `CHECKPOINT_ROW_MISSING`, `CHECKPOINT_HASH`), a head that does not match the newest sealed row (`HEAD_MISMATCH`), a row whose content does not match its hash (`RECORD_HASH`), whose `prev_hash` is not the stored hash of the sealed row before it (`PREV_HASH`), or whose key is no longer stored (`KEY_MISSING`). A missing checkpoint is not a problem (a new installation).
- **Deleting the newest sealed row** is caught two ways: the head no longer matches the rows, and, if the head was put back to match, the checkpoint (which lives in Script Properties, outside the database) is ahead of it. Deleting a row from the middle breaks the next row's `prev_hash`. A gap the sealer already recorded is not a problem, because sealing links to the previous sealed row, not to `seq - 1`.
- **The verifier** reads pages of 1,000, can start at any `seq` (linking to the sealed row before it), and takes an optional deadline: it finishes the page it is on and returns `{verifiedTo, ok, problems, complete}` with `complete: false`; the head and checkpoint checks run only when it reached the end. It lists at most 100 problems; the security event `AUDIT_CHAIN_BROKEN` holds the first 20. Every problem raises `ALARM_AUDIT = 1`, one event and one mail, and the mail has problem types and `seq` numbers only, never row content. **Nothing in the spec clears `ALARM_AUDIT`** and a clean run does not: after investigating, the owner deletes the property by hand in Script Properties (T1.11 could add an owner function for it if you prefer).
- **Missing `ALERT_EMAIL`, or a mail that fails, never stops the work**: the event is still recorded, the alarm still set, and a warning is logged.
- **`Audit.row_`** takes the handler's `ctx`; with no `ctx.user` (a job) the actor is `SYSTEM`. It also takes an optional `requestId` of its own, for a read action that writes one audit row under a derived id (`export:{exportId}`, T4.2). A row the table would refuse (missing names, no request id, non-text reason) is an `INTERNAL` error at the line that built it. Secrets are dropped by exact key name at every depth, through arrays too.
- **Test helper:** `tests/v2/helpers/fakes.js` gained `properties.delete(key)`, so a test can remove a Script Property.

- **Handler names** follow the file layout of section 2: `Module.verb_` for files that hold one group of actions (`ActTimer.start_`, `ActEntries.list_`, `ActReports.summary_`, `ActUsers.create_`), `Module.groupVerb_` for files that hold several (`ActCatalog.clientsCreate_`, `ActWorkspaces.membersAdd_`, `ActSystem.authVerifyCode_`). ## 2026-11-17 · T1.8 · Noted, no answer needed: how the request pipeline fills the gaps in section 4.4

Each point is pinned by a test in `tests/v2/pipeline.test.js` or `tests/v2/doget.test.js`; say if any should change.

- **`ACTIONS` is empty until T1.9.** The pipeline is tested with fixture actions registered inside the test's app context. `Auth.gs` owns the map (spec section 2), and T1.9 fills it and writes the permission matrix.

- **Super Admin and workspaces.** Step 6 says a Super Admin "passes every workspace check". Read as: no membership and no `ws_role` needed, for any workspace that exists. Archived workspaces stay read-only for everybody (section 7.1, rule 5). To know which workspaces exist, a Super Admin's cached account (`acct:{gen}:{email}`) also carries the list of all workspaces.
- **For T2.1, which needs to know this:** the cached account embeds each membership's workspace name, status and time zone, and a Super Admin's copy lists all workspaces. So `workspaces.create`, `.update` and `.archive` must bump `gen:acct` as well as `gen:ws:{id}`, or the pipeline sees the old status for up to 60 seconds. Writes are not at risk: they assert `status = 'ACTIVE'` inside the transaction.
- **What a refusal says.** Not a member, a workspace that does not exist, an inactive membership and a failed workspace-admin check all give the same `FORBIDDEN` with the same text, so ids cannot be probed. A member of an archived workspace on a write gets `FORBIDDEN` with "archived and read-only". A missing or malformed `workspaceId` on a workspace action is `VALIDATION` (field `workspaceId`), before membership is looked at.
- **`ws: 'optional'`** is supported (the catalogue marks `app.bootstrap` "optional"): no `workspaceId` means no workspace; one that is sent is checked like any other.
- **The email.** Trimmed, then it must be printable ASCII and at most 254 characters, then lower-cased. The order matters: the Kelvin sign (U+212A) lower-cases to a plain `k`, so `flinK.test` would otherwise pass for `flink.test`. `COMPANY_DOMAIN` is compared trimmed and lower-cased; a missing or blank one is `INTERNAL` (fail closed, no database call). A wrong domain is refused before any database call.
- **The envelope** must be an object with `v = 1` and only `v`, `requestId`, `workspaceId`, `grant`, `payload`; otherwise `VALIDATION` (field `envelope`, `v`, or the unknown name). It is checked at step 8 with the payload, and the earlier steps read `workspaceId` and `grant` defensively. `payloadHash` is the hash of the normalised payload, so a retry that trims differently still hashes the same.
- **The handler's context** is section 4.4's plus `action`, `grantToken`, `rateLimit` (writes only), `setting(key[, workspaceId])`, and on `workspace`: `wsRole` (null for a Super Admin who is not a member) and `isWsAdmin`. Handlers pass `Auth.dbCtx_(ctx)` to `Db.tx_`. Settings are read once per request: for a write, before the handler (the rate limit needs them); for a read, only when the handler first asks. With warm caches a read costs no Turso call at all.
- **The response.** Only `{ok, data, serverNow}` on success (no `serverNow` on errors, as in section 4.2). `details` is passed on only where section 4.3 defines it (`field`, `rule`, `until`/`hard`, and `retryAfterSeconds: 60` for `RATE_LIMITED`); everything else is dropped, because the Turso client's `DB_UNAVAILABLE` details hold the failing call's text, which includes the database host. Those details go to the log as a warning. `INTERNAL` always has the fixed text and `details.correlationId`; the real cause is logged as an error line under that id, with emails and anything that looks like a token or key replaced.
- **The log line** is `request action=<name> outcome=<OK|CODE> ms=<n> user=<id>`: the action only once it is a registered name (never text the caller made up), the user by id and only once the account is loaded.
- **`MAINTENANCE`** (a Script Property in section 8, set by `ownerMaintenance(on)`) has no step in section 4.4 and no code in 4.3. Not enforced yet; to be decided with T1.11.
- **`doGet`**: only the exact lower-case names `user`, `admin`, `superadmin` select a view, anything else is the user view; the frame mode follows the view actually served. Title "FLINK Time", mobile viewport tag.
- **`tests/v2/helpers/seed.js`** is in the layout of section 2 but no ticket names it, so it was written now, because T1.8 needs accounts. It has the standard world of section 10 plus `admin3` (an Admin who belongs to nothing, for the "Admin non-member" column of T1.9) and `gone` (inactive).

## 2026-11-17 · T1.7 · Noted, no answer needed: how settings are stored, cached and read

- **One cached snapshot.** Section 5.4 caches "merged settings" under `settings:{gen}` without a workspace id, so the cache holds every row of the `settings` table as `{ "GLOBAL": {key: value}, "<workspace id>": {key: value} }`, for 5 minutes. A read resolves **the workspace's own row, then the GLOBAL row, then the catalog default**; a GLOBAL-scope setting never looks at workspace rows. `false` and `0` are values, not "missing".
- **Bad rows are ignored, an unreadable database is an error.** A row with an unknown key, bad JSON, a value outside its range, a workspace row for a GLOBAL setting, or a scope that is neither `GLOBAL` nor a workspace id is skipped with a warning that names the row but not its value. If the table cannot be read at all, `Config.get_` throws `DB_UNAVAILABLE` instead of assuming defaults, because defaults could silently relax a rule (for example `ALLOW_USER_DELETE_ENTRY`).
- **Settings are read with the read-only token.** `settings.patch` (not yet built) must write through `Db.tx_`, then bump `gen:settings`, and `gen:ws:{id}` for a workspace-scope row (spec section 6.2).
- **`Config.checkSetting_(key, value, scope)`** is provided now for `settings.patch`: it checks the key, the scope (a GLOBAL-scope setting cannot be set per workspace) and the value, and returns the normalised value and the JSON to store.
- **Wiring left to T1.8.** Earlier notes said T1.7/T1.8 must pass `RATE_LIMIT_WRITES_PER_MIN` to `Db.tx_` (as `ctx.rateLimit`) and `TIMER_CLIENT_SKEW_SECONDS` to `Util.clampClientTime_`. The values are now available through `Config`; the request pipeline should call `Config.load_()` once per request and use `Config.value_(snapshot, key, workspaceId)`, because each `Config.get_` costs two cache reads.

## 2026-11-17 · T1.6 · Noted, no answer needed: how the schema checker fills the gaps in section 6.1

Each of these is pinned by a test in `tests/v2/validate.test.js`; say if any should change.

- **Optional means absent or null.** A field with `?` may be missing (left out of the result: "leave unchanged") or `null` (kept as `null`: "clear it"). Section 6.2 needs the second reading, for example `users.setAdminLimit` takes "`int:0:50` or `null` for the default" and `entries.update` must be able to remove a project. A required field may be neither.
- **Order of complaints.** Unknown fields are reported first (so a mass-assignment probe stops there), then the schema's fields in the order the schema lists them. `__proto__`, `constructor` and similar names are just unknown fields.
- **Text length counts characters, not UTF-16 units**, because the database `CHECK`s use SQLite `length()`. 120 emoji fit a 120-character name.
- **Tab and newline are allowed only in text whose maximum is 500 or more** (descriptions, notes, reasons); names and shorter text allow neither. The spec says "except tab and newline in notes and descriptions" but the schema type does not say which fields those are; the limits (500 and 2,000 against 120 and 60) do.
- **Always refused in text:** other control characters (including carriage return and the C1 range), U+2028/U+2029, and lone surrogates. The last two go beyond the spec: they would otherwise reach the database and the exports as invisible line breaks or broken characters.
- **`id` is lower-case only** (no case folding, so an id can never match two different rows); **`code` is not upper-cased for you** (`abc` is refused); **`email`** is trimmed, lower-cased and must be ASCII with a dotted domain and a letter-only last label (internationalised addresses are refused; the database also requires lower-case).
- **`ms`** allows 10 years of 365.25 days either side of the server clock, ends included. **`cursor`** is passed through untouched (no trim), 1 to 200 characters, no control characters.
- **Formula neutraliser:** copied from `Validation.sanitizeCellValue` and `ExportService.escapeCsv`. Same rule (apostrophe in front of a string that starts, after spaces, with `= + - @` tab CR LF, except plain numbers). Three differences: the 50,000-character cap is applied after the apostrophe so a cell never exceeds the Sheets limit, a cut never leaves half a surrogate pair, and a `NaN`, object or date is refused instead of being turned into text.
- **A source-file quirk worth knowing:** an escape typed as ` ` or ` ` in a file-writing tool call was turned into the real character, which ends a line in JavaScript and broke a regex. The files are fixed and a test now fails if either character appears literally in `apps-script-v2/` or `tests/v2/`.

## 2026-11-17 · T1.5 · Noted, no answer needed: choices where the spec is silent

- **`Util.clampClientTime_(clientAt, now, skewSeconds)`** takes the skew as an optional third argument (default 120) because the spec lists two. T1.7 and T1.8 must pass `TIMER_CLIENT_SKEW_SECONDS`. A `clientAt` that is not an integer time is not trusted at all (the server time is used).
- **`Util.hmacSha256Hex_(key, message)`** uses the spec's order, `HMAC_SHA256(key, message)`; Apps Script's own function takes `(value, key)`. Both strings are used as the UTF-8 text they are, so the 64-hex-digit audit key is not decoded.
- **Hashing never relies on a platform charset.** `Util.sha256Hex_` and `hmacSha256Hex_` turn strings into UTF-8 bytes themselves; a lone surrogate becomes U+FFFD (as in Node), so odd text in a description cannot make a request fail.
- **The report cache key** is `rep:{wsId}:{wsGen}.{repGen}:{digest}`. Section 5.4 says a report is invalidated by both `gen:ws:{wsId}` and `gen:rep:{wsId}` but shows one `{gen}`; the two numbers are joined so that bumping either changes the key.
- **A cache key over 250 characters is silently not cached** (CacheService would throw). Only an email of about 235 characters or more could reach that, and such a user would just be served uncached.
- **Date helpers** accept years 0001 to 9999; narrower ranges, if wanted, belong in `Validate.gs` (T1.6).
- `Migrations.gs` now hashes with `Util.sha256Hex_` (the T1.3 note asked for this); it keeps its own sender.

## 2026-11-17 · T1.4 · Noted, no answer needed: choices where the spec is silent

`Db.gs` follows section 5.3 branch for branch. These points are not in the spec, so the implementer chose and recorded them here; say if any should change.

- **A request-level error from Turso** (well-formed response whose first result is `{type:"error"}`) maps to `DB_UNAVAILABLE` (retryable), or `BUSY` if the message says the database is locked. Rationale: the outcome is not known, and the page retries with the same request id, which is safe. Phase 0 test 4 should record what real Turso sends.
- **A locked-database message beats `onError`.** If an `exec` step has `onError: CONFLICT` and the database says `SQLITE_BUSY`, the caller gets `BUSY`, not a false conflict.
- **Rate limit source.** `Db.tx_` reads `ctx.rateLimit` (default 60). T1.7 and T1.8 must pass the `RATE_LIMIT_WRITES_PER_MIN` setting there.
- **Usage counter.** Key `usage:{UTC yyyy-mm-dd}`, value `{"read":n,"written":n,"calls":n}`. CacheService keeps a value at most 6 hours, so the counter restarts after 6 idle hours; the hourly health job must copy it into `job_runs` before then, and the numbers are approximate by design. The spec does not say which time zone the "day" uses; UTC was chosen.
- **`INTERNAL` messages are generic** ("The database rejected a statement."); the SQL error text goes in `details.error` for the log, never in the message.
- **New spec-adjacent code in `Config.gs`:** `ERROR_CODES_` and `AppError_` (spec section 3 and 4.3), checked against the spec's own table by a test. T1.7 adds the settings catalog on top.
